# 上游 P1 稳定性增强实施计划

## 执行规则

本计划仅实施上游评估中确认的两项 P1 稳定性增强：出站 HTTP 请求体可重放以支持 HTTP/2 transport 的透明重试，以及 AWS Bedrock 请求随客户端断连取消。实现必须复用现有 `BodyStorage` 的内存/磁盘生命周期，不得引入常驻缓存、后台循环、计费、额度、音视频、任务或多数据库逻辑。每个 Phase 完成后更新本文件并复核 `plan.md`。

## Current State

当前项目已通过 `BodyStorage` 保存部分 JSON 出站请求体，并在 `RelayInfo.UpstreamRequestBodySize` 中保存长度用于写入 `ContentLength`；但 HTTP 请求的 `GetBody` 为空，因此 HTTP/2 在请求体已写入后遇到 stream reset 时不能安全透明重试。`memoryStorage` 和 `diskStorage` 也没有返回独立 reader 的接口。

AWS Bedrock 适配器目前基于 `context.Background()` 创建上游调用 context。客户端断开后，非流式与流式调用会继续直到完成或超时，且取消错误可能进入通用重试路径。

## Target State

JSON 出站请求应在不复制内存 payload 的前提下提供 `GetBody` 工厂：内存存储返回独立 `bytes.Reader`，磁盘存储按需打开独立文件描述符。公共请求构造统一恢复 `ContentLength` 和 `GetBody`，原有 caller 的 storage close 仍负责根存储生命周期。

AWS Bedrock 调用应从 Gin 请求 context 派生，客户端断开或请求超时应取消 InvokeModel/stream 消费并标记为不重试；仍保留全局 relay timeout 上限。

| 范围 | 计划改动 |
| --- | --- |
| `common/body_storage.go` | 在内存与磁盘存储实现独立 reader 工厂。 |
| `relay/common/relay_info.go`、`relay/common/outbound_body.go` | 保存与创建出站请求的 `GetBody` 工厂。 |

| `relay/channel/aws/relay-aws.go` | 将 Bedrock context 绑定到客户端请求，并停止取消后的流消费/重试。 |
| 相关 `*_test.go` | 覆盖内存、磁盘、关闭、请求元数据和 AWS context 取消。 |
| `plan.md`、`.plan/20260825-04.md` | 记录实施和验证。 |

## Rollback Plan / Risks

请求体重放只针对已通过 `NewOutboundJSONBody` 创建的 JSON body，不改变原始 multipart/form-data 或 WebSocket 传输。`GetBody` 必须返回独立 cursor，不能复用根 storage 的读位置；磁盘 reader 的 close 只能关闭子文件句柄。AWS 取消仅传递已有客户端生命周期，不增加额外重试；取消时使用 skip-retry 避免重分发造成重复上游请求。任何异常均可通过回滚本次单一提交恢复。
