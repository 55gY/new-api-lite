## 问题背景（用户报告）

渠道测试返回 `invalid character '<' looking for beginning of value`，且需要把测试相关英文报错改为中文说明，并实测给定上游为何失败。

- 上游 BaseURL：`https://agentrouter.org/v1`、`https://ps.air-outer.com/v1`
- 端点类型：OpenAI；测试模型：`claude-opus-4-8` / `claude-opus-4-7` / `claude-opus-4-6`

## 根因（已实测确认）

两个上游对本服务器的请求**返回 HTTP 200 + `Content-Type: text/html`**，响应体是**阿里云 WAF 滑块人机验证页**
（特征：`aliyun_waf_aa`、`initAliyunCaptcha`、`sceneId`、"访问验证"）。

- 因为状态码是 200，网关不会走错误分支（`service.RelayErrorHandler` 未触发），
  直接在 `relay/channel/openai/relay-openai.go:217` 执行 `common.Unmarshal(responseBody, &simpleResponse)`；
- Go 的 JSON 解析器读到首字符 `<` 即报 `invalid character '<' looking for beginning of value`；
- 该原始错误经 `controller/channel-test.go` 的 `TestChannel` 原样回显到前端，故使用者只看到晦涩的英文。

实测结论：2 个域名 × 3 个模型 = 6/6 组合全部被 WAF 拦截；GET `/v1/models`、根路径、无鉴权请求同样返回验证页，
说明与密钥、模型名无关，是**出口 IP 被上游 WAF 要求人机验证**。两域名 WAF 指纹（`aliyun_waf_aa` 值、userId）一致，属同一后端。

### 关键实现

1. `detectNonJSONUpstreamResponse(resp)`：在 `DoResponse` 之前，仅当 `Content-Type` 为 `text/html` /
   `application/xhtml+xml` 时判定为网页响应，返回中文说明（含状态码、Content-Type、响应片段）。
   **只拦截明确的网页类型**，JSON、SSE(`text/event-stream`)、`text/plain`、无 Content-Type、二进制均不受影响。
2. `describeKnownInterceptPage(preview)`：识别阿里云 WAF、Cloudflare、通用 captcha、404、502/504、nginx 默认页，
   给出更精准的中文原因与处置建议。
3. `LocalizeChannelTestErrorText(raw)`：模式匹配（由具体到宽泛）翻译为中文，**并在末尾保留 `（原始错误：…）`**，
   不丢失排查信息；未命中模式（含已中文化文本）原样返回。
   覆盖：非 JSON/JSON 截断/字段类型不符、401/403/404/429/500/502/503/504、
   DNS 解析失败、连接被拒/被重置、超时（context deadline / Client.Timeout / i/o timeout）、
   TLS 握手与证书、代理连接、EOF、模型不存在、参数不合法、usage 缺失、流式响应异常等。
4. `TestChannel` 与 `testAllChannels`：回显给前端的 `message`、写入 ability 测试记录的原因、
   以及自动禁用原因，统一使用中文化文本。

## 追加发现（同日，用户本机实测）

用户在本机运行时得到的是**应用层 401**，而非 WAF 网页：

```
bad response status code 401, message: unauthorized client detected, ...
body: {"error":{"message":"unauthorized client detected, ..."},
       "message":"UNAUTHENTICATED","success":false,"type":"unauthorized_client_error"}
```

结论修正：本项目所在沙箱出口 IP 被上游 WAF 挑战（拿不到应用层响应，故只观察到 HTML 验证页）；
而用户本机可穿过 WAF 到达应用层，上游应用层**明确拒绝“非指定客户端”的调用**
（`type=unauthorized_client_error`）。即该上游存在**反中转/反网关**策略，
只允许其文档列出的指定客户端直接调用；这既不是密钥问题，也不是本网关配置问题。

因此两层现象都真实存在，只是观察位置不同：
- 网络层（WAF 挑战）→ 表现为 `invalid character '<'`（已由本次网页响应拦截解决说明问题）；
- 应用层（客户端限制）→ 表现为 401 `unauthorized_client_error`。

补充改动：在中文化规则表中，把 `unauthorized_client` / `unauthorized client` / `client not allowed`
规则**排在 401/403 规则之前**，避免被误判为“密钥无效”，并明确提示这是上游的客户端/中转限制。
新增单测 `TestLocalizeChannelTestErrorTextUnauthorizedClient` 使用真实报错原文做回归保护。

## 追加（2026-08-02）：路径 B 落地验证 + C7 回归修复

### 背景
用户上游服务端为其自有部署（第三方一键封装版），与 new-api-lite **不在同一台服务器**，
无法修改上游程序，需通过网关侧「请求头覆盖」呈现上游期望的客户端身份来完成对接。

### 发现并修复：C7 引入的回归（重要）
`.plan/20260722-01.md` 的 C7 曾直接复用 `common.ValidateURLWithFetchSetting` 校验渠道 BaseURL。
但该配置默认值为 `EnableSSRFProtection=true`、`AllowedPorts=[80,443,8080,8443]`、`AllowPrivateIp=false`，
面向的是「用户提交的下载/回调 URL」。套用到**管理员填写的渠道 BaseURL** 会大面积误伤：
自建上游使用局域网地址、`127.0.0.1` 或非标准端口（如 `:3000`、`:9999`）是常规部署方式。

实测复现：创建 `base_url=http://127.0.0.1:9999` 的渠道被拒——
`渠道 BaseURL 未通过 SSRF 安全校验：port 9999 is not allowed`。

修复：改为 `controller/channel.go` 中新增的 `validateChannelBaseURLSafety`，
**只拦截链路本地/云实例元数据地址**（169.254.0.0/16、fe80::/10、metadata.google.internal、metadata.goog），
不限制端口、不禁止内网/回环地址、不对域名做 DNS 解析。
新增 `controller/channel_baseurl_safety_test.go` 双向回归保护（放行自建上游 / 拦截元数据地址）。

### 路径 B 端到端验证（真实实例 + 本地回显上游）
搭建回显上游（记录收到的请求头）+ 启动真实 new-api-lite 实例，走完整渠道测试链路：

| 渠道类型 | 端点类型 | 上游实际收到的 path | 鉴权头 | UA 覆盖 | 结果 |
| --- | --- | --- | --- | --- | --- |
| OpenAI(type=1) | openai | `/v1/chat/completions` | `Authorization: Bearer` | ✅ 生效 | success:true |
| Anthropic(type=14) | anthropic | `/v1/messages` | `X-Api-Key` | ✅ 生效 | success:true |

上游收到的头（示例）：
```
User-Agent: claude-cli/2.1.39 (external, cli)
X-App: cli
Anthropic-Version: 2023-06-01
Anthropic-Beta: claude-code-20250219,oauth-2025-04-20
```

结论：`header_override` 在 `SetupRequestHeader` 之后应用（优先级最高），
可覆盖 `User-Agent` 等任意头，且**渠道测试路径同样生效**。
注意：渠道测试时会跳过 `{client_header:...}` 占位符与 `*` / `re:` 透传规则，故须填**静态值**。
