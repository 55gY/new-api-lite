## 与本批 U1000 删除的关联复核

对已删除的 23 个私有符号进行了源码引用复查。删除的启动/独立日志迁移、quota/cache、性能 Redis helper、Jimeng/Zhipu 私有 DTO、Codex 状态 helper 与 hardcoded ratio helper 均未发现活动调用链。模型、用户、token、Codex、性能和相应 relay 包已被全量测试、竞态检测、启动冒烟或认证/API-token 链路覆盖。

## 兼容性观察（非本轮功能回归失败）

状态接口仍向旧客户端暴露 `enable_task: true`、`quota_per_unit`、`quota_display_type`、价格/货币字段；其中前端当前仅把若干 quota 展示字段写入 localStorage，未发现 `enable_task` 的前端使用，且 task/public routes 已不存在。这些字段没有造成当前功能失败，但与 Lite 的无任务/无计费语义不完全一致，属于后续可单独处理的 API 契约清理，而非 staticcheck 清理引入的回归。

`controller/setup.go` 创建管理员时仍写入历史 `Quota: 100000000`，而用户 self API 返回的 quota 已为 0；这同样未恢复扣费行为，也未阻断初始化或认证流程，但可在后续 Lite 数据模型/响应契约专项中改为中性兼容值。

## 未覆盖范围

本次不连接真实供应商、Redis、邮件、OAuth 或外部网络，因此未验证特定上游账户、速率限制、流式响应的实际供应商行为。已有 Go 单元/集成测试、全量 race 检测与本地鉴权/路由冒烟覆盖应用内回归；生产部署仍应在真实配置中进行渠道级验收。

## 结论

截至本次体检，项目保留的启动迁移、设置初始化、管理员登录、后台管理、API token 与 models/chat/responses/embeddings 路由认证链路均正常，且没有证据表明 staticcheck/U1000 清理破坏了这些功能。发现的两项历史 status/quota 兼容字段问题不影响当前运行，但建议作为独立低风险 Lite 契约清理任务处理。
